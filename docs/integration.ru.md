# Подключить обновления заказов к существующему приложению

[← README](../README.md) · [Версии](index.md) · [English](integration.en.md)

## 1. Что добавляется в приложение

Relay client — одна сессия соединения для одного аккаунта и логического потока. Он получает событие, ждёт бизнес-обработчик, сохраняет позицию и только после этого считает событие завершённым. После обрыва запрашивает события, следующие за этой позицией.

Подходит для состояния заказов, оповещений и панелей, где переподключение должно сохранять прогресс. Обычного EventSource достаточно, если пропуск обновления допустим или экран всегда загружается заново целиком. Здесь нужен [протокол relay](PROTOCOL.ru.md): библиотека не восстановит историю, которую сервер не хранил.

Приложение отвечает за вход и бизнес-действия. Библиотека — за разбор потока, задержки повторов, порядок обработки и сохранения позиции, отмену соединения. Необязательный Node-сервер хранит историю в памяти для примера; долговечное хранение остаётся задачей рабочего сервера.

## 2. Разместить интеграцию в проекте

Зависимости и первый полный модуль приведены в [Get started](../README.md). Обычная структура:

```text
src/
  auth/session.ts                 существующая OAuth-сессия и транспорт
  orders/order-updates.ts         копия examples/orders.ts
  orders/order-page.ts            запуск при открытии, остановка при закрытии
server/
  events-route.ts                авторизованный endpoint протокола relay
```

[Полный модуль заказов](../examples/orders.ts) · [Адаптер DPoP-сессии](../examples/dpop-session.ts) · [Исполняемый сервер](https://github.com/dlorian59/browser-sse-relay/blob/main/demo/server.mjs).

Фронт и сервер согласуют `/api/events`, поток `notifications`, аккаунт из авторизации и JSON-сообщения `{key,text}`. `key` — бизнес-идентификатор; SSE event ID — отдельная позиция обработки, которую выдаёт сервер. Редактируемая пользователем строка аккаунта не даёт прав доступа.

<a id="receive-orders"></a>
## 3. Получить и применить обновление

Функция `watchOrderUpdates(accountId, authenticatedFetch, applyNotice)` из примера возвращает клиент. Один раз вызовите его `start()`. `applyNotice` получает проверенное уведомление и AbortSignal; обработчик может быть асинхронным. Сессия не продвинет курсор до завершения promise и успешного сохранения checkpoint.

`decodeOrderNotice` проверяет бизнес-поля. Неверный JSON или структура сообщения оставляют событие неподтверждённым и расходуют конечный бюджет повторов. Это намеренное поведение: молчаливый пропуск скрывает пробел в данных. Исправьте сообщение либо восстановитесь по согласованному снимку.

`jsonEventHandler({decode,onData})` — тот же адаптер, если приложение уже создаёт `SseRelayClient` или использует provider фреймворка. Сам по себе он не открывает соединение.

<a id="profiles"></a>
## 4. Выбрать готовые настройки

Начните с `RelayProfiles.NOTIFICATIONS`: его использует `createJsonRelay` по умолчанию. Для более активного списка предусмотрен `RelayProfiles.LIVE_FEED`. Оба профиля ограничены; названия не означают гарантию задержки или пропускной способности.

| Настройка | NOTIFICATIONS | LIVE_FEED |
|---|---|---|
| Всего попыток соединения в сессии | 8 | 8 |
| Задержка повтора | 250 мс–10 с | 250 мс–5 с |
| Тайм-аут подключения / простоя байтов | 10 с / 45 с | 10 с / 30 с |
| Максимум событий в очереди | 128 | 256 |
| Максимальный объём очереди | 1 MiB | 2 MiB |
| Максимальный кадр | 64 KiB | 64 KiB |
| Последние подтверждённые ID | 1024 | 2048 |

Добавьте `...RelayProfiles.LIVE_FEED` в настройки клиента. Собственные `retry`, `limits` и тайм-ауты указывайте, только если приложению нужны другие значения. Профили и вложенные настройки заморожены; клиент копирует значения перед использованием. Heartbeat сервера должен приходить чаще выбранного тайм-аута простоя.

После исчерпания попыток сессия завершается. Явное создание новой сессии или кнопка подключения запускает новый конечный бюджет; скрытого бесконечного цикла нет.

<a id="lifecycle"></a>
## 5. Согласовать жизнь экрана и курсора

`createJsonRelay` создаёт checkpoint в памяти своей сессии. Состояние приложения должно жить столько же. Курсор сообщает, что уже обработано, но не содержит сами заказы.

- `stop()` отменяет соединение и будущие обработчики. Уже начатая бизнес-операция должна учитывать свой сигнал.
- `await logout()` также ждёт текущую работу и очищает checkpoint аккаунта/потока. После этого удаляйте данные экрана и OAuth-сессию по правилам приложения.
- Для постоянного checkpoint нужны соответствующие сохранённые данные приложения или восстановление снимка после reload. Один курсор пропустит события, необходимые пустому экрану для восстановления.

Бизнес-действие может завершиться раньше, чем сохранение checkpoint вернёт ошибку. Делайте действие идемпотентным: например, заменяйте заказ по его бизнес-ключу. Браузер не может одной транзакцией подтвердить удалённый платёж и локальный курсор.

## 6. Восстановиться после удаления истории

Если нужная позиция больше не хранится на сервере, клиент возвращает `resync`. Получите авторизованный снимок согласованных данных и курсора; сначала примените данные, затем создайте клиент с `initialCursor`. [Полный разбор восстановления](v0.1.0/guide.ru.md#snapshot-after-resync).

Готовый React-компонент [SseFeed](https://github.com/dlorian59/browser-sse-relay-react) выполняет этот порядок через `snapshotUrl` и кнопку восстановления; `loadSnapshot` предусмотрен для готового SDK приложения. Это ограниченное окно записей для экрана, а не долговечный бизнес-журнал.

## 7. Подключить авторизацию

Используйте готовый авторизованный fetch приложения. Если OAuth поддерживает DPoP, `createDpopFetch` подписывает каждый запрос привязанным ключом и обрабатывает один nonce challenge. [Руководство DPoP](dpop.ru.md) объясняет жизнь ключа, refresh, серверные проверки и CORS. Relay не выполняет вход и не превращает Bearer-токен в привязанный.

## Типичные ошибки интеграции

| Симптом | Причина и исправление |
|---|---|
| После reconnect не хватает заказов | Курсор сохранился, а список — нет. Восстановите соответствующие данные или снимок. |
| Действие выполнилось дважды | Обработка завершилась, checkpoint не сохранился. Используйте бизнес-ключ идемпотентности или upsert. |
| Повторяются ошибки декодирования | Поля сервера отличаются от контракта. Исправьте данные, не подтверждайте неверное сообщение. |
| Спокойный поток переподключается | Тайм-аут меньше интервала heartbeat. Согласуйте их. |
| После reload отказ авторизации | Ключ DPoP больше не соответствует токену. Восстановите OAuth-сессию или получите новый привязанный токен. |
